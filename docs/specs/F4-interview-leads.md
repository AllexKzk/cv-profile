# F4. Интервью «Кого вы ищете?» + заявки

**Статус:** done
**Зависит от:** F3
**Ветка:** `step/F4-interview-leads`

## Цель
Кнопка «Кого вы ищете?» запускает короткое интервью: агент задаёт вопросы виджетами (клик по
вариантам, вилка, свой ответ или свободный текст), собирает бриф вакансии и показывает его
карточкой с быстрым фитом против резюме. Из карточки рекрутер по явному клику отправляет заявку
Александру в Telegram. Цель — ≈ 2 минуты кликов и 4–5 запросов к LLM на всё интервью.

## Входит
- Схема брифа `VacancyBrief` и описание слотов (виджет, варианты, обязательность) в `shared/` —
  одно определение для промпта, виджетов, tool-схем и заявки.
- Сценарий `interview` в `/api/chat`: промпт-дополнение, tools `askQuestion` (клиентский),
  `submitBrief` (серверный), `showCvSection`.
- `QuestionWidget` (single / multi / range / text, «свой вариант», «Пропустить»), ответ кликом или
  текстом из обычного поля ввода, автопродолжение после ответа.
- `BriefCard`: сводка брифа, быстрый фит, CTA «Отправить Александру» (CTA «Загрузить описание
  вакансии» — в F5, см. вопрос 6).
- Форма заявки (диалог), `POST /api/lead` → Telegram Bot API, zod, rate limit, honeypot,
  подтверждение в чате.
- Тесты (см. «Как проверить»), i18n EN/RU, `.env.example` уже содержит Telegram-переменные.
- shadcn: `input`, `label` (и `checkbox`/`toggle-group`, если понадобятся виджету).

## Не входит
- Запуск интервью из свободного текста («мы ищем фронтенда…») — только кнопкой. В свободном
  чате агент может предложить нажать её.
- Загрузка и анализ вакансии, MatchReport, CTA заявки из отчёта → F5 / F6 (форма и `/api/lead`
  делаются переиспользуемыми).
- Хранение заявок где-либо кроме Telegram, CRM, ответы бота, уведомления пользователю на почту.
- Этапы найма и название компании как вопросы интервью (компания — в форме заявки, этапы — в её
  комментарии; см. вопрос 2).
- Редактирование брифа прямо в карточке (правка — текстом: «вилка до 400k» → новый бриф).

## Ключевые решения

### Слоты брифа
Виджет и варианты для слота задаёт код, а не модель: меньше токенов, одинаковый UI, нет
выдуманных вариантов. Модель передаёт только формулировку вопроса и — где это осмысленно —
подсказки вариантов.

| # | Слот | Вопрос (пример) | Виджет | Варианты | Обяз. |
|---|---|---|---|---|---|
| 1 | `role` | Какую роль закрываете? | single + свой | Frontend, Fullstack, Tech Lead / Team Lead *(модель может подменить)* | да |
| 2 | `seniority` | Какой уровень? | single + свой | Middle, Senior, Lead, Staff+ | да |
| 3 | `mustHave` | Обязательный стек? | multi + свой | ≤ 8 подсказок от модели под роль (TypeScript, Vue, React, Node.js…) | да, ≥ 1 |
| 4 | `niceToHave` | Что будет плюсом? | multi + свой | ≤ 8 подсказок от модели, без уже выбранного | нет |
| 5 | `format` | Формат работы? | multi | Удалённо, Гибрид, Офис | да |
| 6 | `location` | Город офиса / таймзона, помогаете ли с релокацией? | text | — | только если гибрид / офис или нужна таймзона |
| 7 | `domain` | Продукт / домен? | single + свой | Финтех, E-commerce, B2B SaaS, Медиа, Внутренние инструменты *(модель может подменить)* | нет |
| 8 | `employment` | Тип занятости? | single | Полная, Частичная, Контракт / B2B | нет |
| 9 | `salary` | Вилка? | range | от / до + валюта (RUB, USD, EUR) + период (мес / год), gross | нет |
| 10 | `start` | Когда нужен человек? | single | Как можно скорее, В течение месяца, 1–3 месяца, Гибко | нет |

Вопросы идут **раундами по 2–3** (один шаг модели — несколько вызовов `askQuestion`, ответы
отправляются разом): 1–2 → 3–4 → 5–7 → 8–10 → `submitBrief`. Итого 5 запросов к LLM
(≈ $0.005 при ~5k входных токенов на запрос). Агент пропускает слоты, ответ на которые уже
прозвучал в тексте, и не переспрашивает необязательное, на которое нажали «Пропустить».
Обязательный слот без ответа спрашивается ещё раз один раз; если ответа снова нет, бриф уходит
без него, а карточка показывает «не указано» (см. вопрос 3).

Схема `VacancyBrief` (вход `submitBrief`): `role`, `seniority`, `mustHave[]`, `niceToHave[]`,
`format[]`, `location?`, `domain?`, `employment?`, `salary? { min?, max?, currency, period }`,
`start?`, `company?` и `notes?` (≤ 500 символов — что ещё рекрутер сказал текстом). Строки
короткие (≤ 100), списки ≤ 15.

### `askQuestion` — клиентский tool
- Вход: `{ slot, question (≤ 200), options? (≤ 8 строк ≤ 40) }`. `options` учитываются только
  у слотов с подсказками от модели (`role`, `mustHave`, `niceToHave`, `domain`), иначе берутся
  варианты из кода (i18n).
- Выход (zod, хранится в истории): `{ kind: 'options', values[] } | { kind: 'range', min?, max?,
  currency, period } | { kind: 'text', text } | { kind: 'skipped' }`. Значения — подписи
  вариантов, чтобы модель понимала их без словаря. Свободный текст ≤ 2 000 символов, как в F3.
- Без `execute`: стрим заканчивается на вызове, виджет ждёт ответа. Ответ → `addToolOutput`
  (в `ai@7.0.156` так называется, `addToolResult` — deprecated алиас).
- Автопродолжение: `sendAutomaticallyWhen` со своим предикатом — последний шаг ассистента
  содержит `tool-askQuestion` и у всех них есть выход. Готовый
  `lastAssistantMessageIsCompleteWithToolCalls` не берём: он перезапросит и после серверного
  tool, если модель упёрлась в лимит шагов.
- **Ответ текстом.** Поле ввода не блокируется. Если есть неотвеченные вопросы, отправка текста
  не создаёт user-сообщение, а закрывает раунд: первому вопросу — `{ kind: 'text', text }`,
  остальным — `skipped`. Текст показывается в виджете как ответ. Модель сама разберёт его на
  слоты или ответит на встречный вопрос и переспросит.
- Отвеченный виджет сворачивается в строку «Вопрос — ответ» (можно поменять ответ, только пока
  раунд не отправлен).

### `submitBrief` — серверный tool
- Вход — `VacancyBrief`. `execute` считает **быстрый фит кодом**, без LLM:
  - стек: каждый пункт `mustHave` / `niceToHave` ищется в навыках резюме (имя + `aliases`,
    регистр и `.js` не важны) и в стеке мест работы → `inCv: true / false`. Функция
    сопоставления — в `shared/cv/`, её переиспользуют F5–F6;
  - формат: пересечение с `person.openTo` → `match`; только офис, а в `openTo` есть
    релокация → `relocation`; иначе `mismatch`.
- Выход: `{ brief, fit: { mustHave: {name, inCv}[], niceToHave: {name, inCv}[], format } }`.
  После него модель пишет 1–2 предложения: сильные стороны и риски (в том числе домен — в
  резюме сказано, что i-gaming и military не рассматриваются).
- В UI отсутствие навыка — «нет в резюме», а не «не умеет».

### Сценарий
- Сценарий `interview` = базовый промпт + текст свободного чата + дополнение интервью
  (порядок раундов, правила пропуска, «один вопрос — один слот», после ответов на все раунды —
  `submitBrief`, после брифа — обычный Q&A; повторный `submitBrief` только при изменении данных).
  Tools: `showCvSection`, `askQuestion`, `submitBrief`.
- Как клиент выбирает сценарий: кнопка добавляет в user-сообщение («Кого вы ищете?») невидимую
  часть `data-interview`. Сценарий вычисляется из истории: есть `data-interview` → `interview`,
  иначе `free`. Состояние не хранится отдельно, переживает перезагрузку; «Сбросить чат» —
  выход. Повторный клик по кнопке начинает новое интервью (модель ориентируется на последний
  маркер). Для модели маркер — строка «[The visitor started the interview]».
- `MAX_STEPS = 3` хватает: клиентский tool сам останавливает цикл.

### Изменения в `/api/chat` (guard)
- Последним может быть сообщение ассистента, если его последний шаг — `askQuestion` с выходами
  (автопродолжение). Иначе, как в F3, последним должен быть пользователь.
- Выходы `askQuestion` валидируются tool-схемами (`safeValidateUIMessages`), лимит 2 000
  символов на текст — как у user-сообщения.
- Автопродолжение — это обычный запрос: те же лимиты IP / бюджета / дня (см. вопрос 4).

### Заявка: `POST /api/lead`
- Форма — диалог из `BriefCard`: имя, **контакт** (обязательно, 3–100 символов: Telegram, email
  или телефон — формат не проверяем строго), компания, комментарий (≤ 1 000). Скрытое поле
  `website` — honeypot.
- Body: `{ name?, contact, company?, comment?, website, brief, fit, locale }`, `z.strictObject`.
  `brief` / `fit` — из выхода `submitBrief` (клиенту не доверяем: только валидация и экранирование).
  В F6 вместо брифа придёт отчёт — схема body расширяется вариантом.
- Порядок: чужой `Origin` → `403`; невалидно → `400`; honeypot заполнен → `200 ok` без отправки;
  rate limit → `429`; нет env Telegram → `503`; Telegram `sendMessage` (`parse_mode: HTML`, все
  значения экранированы, timeout 10 с) ошибка → `502 send_failed`, детали — в лог.
- Лимиты (Upstash, no-op без env): **1 заявка / сутки на IP**, **20 / сутки на сайт**. Отдельные
  ключи от чата, LLM-бюджет не трогают. Засчитывается только успешно отправленная заявка: ошибка
  Telegram или сети не съедает попытку. После лимита форма вместо отправки показывает ссылку на
  Telegram Александра.
- Сообщение в Telegram (подписи по-русски, значения как ввёл пользователь):
  контакт / имя / компания / комментарий → бриф одной-двумя строками на слот → фит («must-have:
  5/6 в резюме, нет: Go; формат: подходит») → язык сайта и время.
- После `ok` в чат добавляется локальное сообщение ассистента «Заявка отправлена, Александр
  свяжется по <контакт>» с частью `data-lead { briefCallId }`. `BriefCard` по ней показывает
  «Отправлено» вместо CTA (переживает перезагрузку). Ошибка — текст в форме + ссылка на
  Telegram Александра, форма не закрывается и не теряет ввод.

### Что владелец делает руками
1. В Telegram у **@BotFather**: `/newbot` → имя и username бота → получить токен.
2. Написать своему боту любое сообщение (иначе бот не сможет писать первым).
3. Узнать chat id: открыть `https://api.telegram.org/bot<TOKEN>/getUpdates` → `message.chat.id`.
4. Локально: `.env` → `NUXT_TELEGRAM_BOT_TOKEN`, `NUXT_TELEGRAM_CHAT_ID`.
5. Vercel → Settings → Environment Variables: те же две, для Production и Preview.

## Как проверить
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` — зелёные
- [ ] «Кого вы ищете?» → короткое вступление и 2 виджета; клики по вариантам, «свой вариант»,
      вилка, «Пропустить» работают; раунд уходит сам после ответа на все вопросы
- [ ] Ответ текстом вместо клика («сеньор фронт, Vue и TS, удалёнка») — агент засчитывает
      слоты и не переспрашивает их; встречный вопрос посреди интервью — ответ и возврат к
      вопросам
- [ ] Всё интервью ≤ 5 запросов к LLM (лог usage), ≈ 2 минуты
- [ ] `BriefCard`: слоты, отметки стека «есть / нет в резюме», формат, 1–2 предложения о фите
- [ ] Перезагрузка посреди интервью и после брифа — виджеты, ответы, карточка и состояние
      «Отправлено» на месте; можно продолжить отвечать
- [ ] Смена языка: подписи вариантов из кода переводятся, новые вопросы — на языке пользователя
- [ ] Заявка: без контакта не отправляется; с контактом — сообщение в Telegram с брифом;
      HTML в полях приходит текстом; 2-я заявка за сутки → понятная ошибка и ссылка на Telegram; honeypot → `ok`
      без отправки; без env Telegram → ошибка и ссылка на Telegram
- [ ] Тесты: схема брифа и выходов `askQuestion`; сопоставление стека (aliases, регистр) и
      формата; предикат автопродолжения; guard (assistant последним только с выходами
      `askQuestion`); выбор сценария по истории; `/api/chat` interview с `MockLanguageModelV4`
      (вызов `askQuestion` завершает стрим, `submitBrief` возвращает фит); `/api/lead`
      (валидация, honeypot, `Origin`, лимит, экранирование, ошибка Telegram — fetch мокается);
      UI: `QuestionWidget` (виды, свой вариант, пропуск, ответ текстом), `BriefCard`, форма

## Открытые вопросы
1. **Набор слотов** — 10 слотов выше, обязательные `role`, `seniority`, `mustHave`, `format`?
   Предлагаю так; можно ещё сократить, убрав `employment` и `start` (−1 раунд).
   - **Ответ:** вроде да — проверим на практике.
2. **Этапы найма и компания** — не спрашивать в интервью (компания — в форме заявки, этапы — в
   комментарии)? Предлагаю не спрашивать: это не влияет на фит, а интервью короче.
   - **Ответ:** нет, не спрашивать: компания — в форме заявки, этапы — в комментарии.
3. **Обязательный слот без ответа** — после одного повторного вопроса отдавать бриф с «не
   указано» или не выпускать `submitBrief` без него? Предлагаю «не указано»: рекрутер не
   должен застревать.
   - **Ответ:** так: повторить один раз, затем «не указано».
4. **Лимит запросов на IP** — интервью съедает ~5 из 15 запросов за 10 минут; после него и пары
   вопросов легко упереться. Предлагаю поднять `NUXT_IP_REQUEST_LIMIT` по умолчанию до 25:
   стоимость запроса ~$0.001, бюджет держат $1 / IP и дневной лимит.
   - **Ответ:** оставить как есть (15 запросов / 10 мин).
5. **Лимиты заявок** — 3 / час на IP и 20 / сутки на сайт?
   - **Ответ:** 1 заявка в сутки на IP; на сайт — 20 / сутки.
6. **CTA «Загрузить описание вакансии» в `BriefCard`** — показывать уже сейчас (до F5 — заглушка
   «скоро») или добавить в F5? Предлагаю добавить в F5, чтобы не показывать заглушку.
   - **Ответ:** да, в F5, опционально.

## Дополнение (после реализации)
- **Ответ кликом не меняется.** Ответ уходит в `addToolOutput` сразу, виджет сворачивается
  в строку «вопрос — ответ». Поменять можно текстом («поменяй уровень на Lead»): агент учтёт.
- **Раунд считается отвеченным, только если вопросы — последние части сообщения.** Без этого
  ответ модели, пришедший без нового шага, снова запускал отправку (бесконечный цикл, ловится
  тестом).
- Агент пропускает целые раунды, если ответы уже прозвучали: в ручной проверке интервью заняло
  **4 запроса и ≈ $0.004** (раунд «формат / домен» закрыл ответ текстом).
- Лимиты заявок вынесены в env: `NUXT_LEAD_IP_DAILY_LIMIT` (1), `NUXT_LEAD_DAILY_LIMIT` (20).
  Ключи Redis отдельные от чата.
- Коды ошибок `/api/lead`: `invalid`, `forbidden`, `rate_limit`, `unavailable` (нет env
  Telegram, `503`), `send_failed` (`502`). В форме при любой ошибке есть ссылка на Telegram.
- В `BriefCard` стек показан сразу после роли, затем остальные поля; превью ссылок в сообщении
  Telegram выключено.
- Не проверено вживую: успешная отправка в Telegram (нет токена бота) и лимиты заявок с
  Upstash. Оба пути покрыты тестами с моком `fetch` и хранилища.
