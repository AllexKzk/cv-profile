# F6. Уточнения и отчёт о совместимости

**Статус:** review
**Зависит от:** F4, F5
**Ветка:** `step/F6-match-report`

## Цель
Промежуточный блок F5 заменяется полноценным отчётом `MatchReport`: процент и уровень, разбивка по
категориям, сильные стороны и риски с evidence из резюме, полный список требований. Рекрутер
прямо в отчёте уточняет, насколько критичны пробелы в must-have, — процент пересчитывается кодом
сразу, без запроса к LLM. Из отчёта по явному клику уходит заявка с его сводкой в Telegram.

## Входит
- `MatchReport` вместо `VacancyMatchBlock` (та же часть `tool-analyzeVacancy`, одна строка реестра;
  старые истории из localStorage рендерятся новым компонентом).
- Блок уточнений внутри отчёта: до 5 must-have с пробелами, у каждого «Обязательно / Желательно /
  Не важно»; пересчёт через `computeMatchScore`.
- Часть `data-priorities` (ответы на уточнения) в том же сообщении ассистента: переживает
  перезагрузку, модель видит её короткой строкой в следующих вопросах.
- Сильные стороны и риски — списки, собранные кодом из требований (не LLM).
- CTA «Отправить отчёт Александру»: `LeadDialog` + `/api/lead` с вариантом body `report`, сообщение
  в Telegram со сводкой отчёта. После отправки — «Отправлено» (`data-lead`, как у `BriefCard`).
- Правка промпта `match`: не спрашивать текстом о критичности — это делается в блоке.
- shadcn: `toggle-group` (переключатель важности), `collapsible` (полный список требований).
- Тесты, i18n EN/RU.

## Не входит
- Tools `askRequirementPriority` и `showMatchReport` — заменены решением ниже (вопрос 1).
- Ручная смена важности любого требования (только до 5 уточнений из правила ниже).
- Шаринг отчёта ссылкой, PDF отчёта → бэклог.
- Изменения анализа (`analyzeVacancy`, промпт классификации, формула и веса F5).
- Эвал качества на наборе вакансий → F7.

## Ключевые решения

### Уточнения без LLM вместо `askRequirementPriority` + `showMatchReport`
План (ARCHITECTURE §3.4) предполагал: модель после анализа вызывает клиентский
`askRequirementPriority`, рекрутер отвечает, автопродолжение, модель вызывает `showMatchReport`,
сервер пересчитывает, модель пишет вывод. Предлагаю иначе:

- **Что спрашивать решает код, а не модель.** Правило детерминированное: требования `must` со
  статусом `missing`, затем `partial`, в порядке из анализа, **не больше 5**. Модель добавила бы
  к этому правилу только выбор формулировки — и стоила бы лишних шагов.
- **Пересчёт локальный.** Выход `analyzeVacancy` уже содержит всё для отчёта (требования, важность,
  статусы, evidence). Клик → `computeMatchScore(requirements с новой важностью)` на клиенте →
  процент, уровень, категории и списки обновляются мгновенно. Сервер и модель не участвуют.
- **Почему так:** $0 и 0 секунд вместо ещё одного запроса из 2 шагов (≈ 11k входных токенов на
  шаг, ≈ $0.003 и 5–10 с ожидания — больше, чем сам анализ F5); не нужно чинить выбор сценария
  при автопродолжении (сейчас `chatScenario` вернёт `free` / `interview`, а не `match`); вакансия
  не отправляется повторно; ответ можно поменять в любой момент, а не один раз за раунд.
  Механику клиентских tools уже показывает интервью F4.
- **Цена отказа:** нет «агента, который сам решает уточнить»; текст вывода модели, написанный до
  уточнений, может упоминать риск, который рекрутер потом пометил «не важно». Смягчение — списки
  сильных сторон и рисков в отчёте считает код, и они обновляются; промпт просит модель говорить
  о рисках без категоричности («в резюме нет Go — уточните, насколько он критичен, в блоке»).

Значения: «Обязательно» = `must` (как в анализе, по умолчанию), «Желательно» = `nice` (вес 1),
«Не важно» = `none` (вес 0, требование уходит из процента и из рисков, в списке помечено
«не важно»). Точка расширения F5 (`ScoreImportance` с `'none'`, веса — параметр) используется
как есть, формула не меняется.

### `data-priorities`
- Схема: `{ source: toolCallId анализа, values: Record<имя требования, 'must' | 'nice' | 'none'> }`
  (≤ 5 ключей, имя ≤ 80 — имена уникальны после дедупликации F5). Хранятся только изменённые
  значения; «Сбросить уточнения» удаляет часть.
- Клиент кладёт часть в то же сообщение ассистента сразу после `tool-analyzeVacancy` (через
  `setMessages`, без запроса). В ленте не рендерится, `MatchReport` читает её по `source`.
- Для модели — одна строка вместо JSON: `[The visitor clarified priorities: Go — not important;
  Kubernetes — nice to have. Updated level: good]`. Процента нет — как в F5, модель его не
  пересказывает. Так вопрос «а если Go не важен, он подходит?» отвечается по истории.
- Guard проверяет часть схемой (как остальные `data-*`).

### Дизайн `MatchReport`
Карточка (`CvCard`) сверху вниз; на мобильном всё в одну колонку.

1. **Шапка.** Слева — должность и компания. Справа — крупный процент и бейдж уровня в цвете
   уровня (`success` / `warning` / `destructive` токены). Под процентом — «по 14 требованиям,
   из них 9 обязательных». Если есть уточнения — строка «С учётом ваших уточнений · Сбросить».
   `percent === null` — «Недостаточно данных для оценки» вместо цифры.
2. **Уточните критичность** (только если правило дало кандидатов). Заголовок и подсказка
   «Процент пересчитается сразу». Строка на требование: иконка статуса, имя, evidence для
   `partial` («есть Node.js, Go — нет»), справа переключатель «Обязательно | Желательно | Не важно»
   (`toggle-group`, семантика radio group, доступен с клавиатуры). На мобильном переключатель
   переносится под имя.
3. **По категориям.** Категории, где есть оцениваемые требования (`byCategory`): подпись,
   горизонтальная полоса процента (токены уровня), «3 из 4». Порядок — как в
   `REQUIREMENT_CATEGORIES`. Категорий «зарплата» нет — в анализе её нет.
4. **Сильные стороны / Риски** — две колонки на десктопе.
   - Сильные стороны: до 4 требований `match`, сначала `must`, с evidence.
   - Риски: `must` + `missing` (❌), `must` + `partial` (⚠️, с evidence), затем `must` + `unknown`
     с пометкой «уточнить на собеседовании» (❔). Требования «не важно» сюда не попадают. До 5,
     остальное — в полном списке. Пусто — «Критичных пробелов нет».
5. **Все требования (N)** — свёрнуто (`collapsible`). Внутри — как в F5: группы по статусу,
   у каждого бейдж важности (с учётом уточнений) и evidence.
6. **CTA.** Основная кнопка «Отправить отчёт Александру» → `LeadDialog`. После отправки — строка
   «Отправлено» вместо кнопки. Ошибка анализа и скелетон «Анализирую вакансию…» — как в F5.

Текст вывода модели (2–4 предложения) остаётся под блоком, как в F5.

### Заявка из отчёта
- `leadRequestSchema` становится объединением по полю `kind`: `brief` (как сейчас — `brief` +
  `fit`) и `report`: `{ source, title, company, requirements: { name, category, importance,
  status }[] ≤ 25, priorities }` — без evidence, чтобы уложиться в 16 KB.
- **Процент считает сервер** заново по присланным требованиям и уточнениям (`computeMatchScore`),
  цифре от клиента не доверяем. Лимиты, honeypot, `Origin`, коды ошибок — как в F4, ключи лимитов
  общие (1 заявка / сутки на IP на любой вид).
- Сообщение в Telegram: контакт и форма → «<b>Отчёт по вакансии</b>»: должность, компания,
  процент и уровень, «с уточнениями: Go → не важно», must-missing, must-partial, ❔ must-unknown,
  счётчики по статусам → язык сайта.
- `LeadDialog` принимает вместо `brief` / `fit` готовое тело варианта (`brief` или `report`),
  остальное без изменений; `data-lead.source` = toolCallId анализа.

### Бюджет
F6 не добавляет запросов к LLM: уточнения и пересчёт локальные, `data-priorities` в истории —
десяток токенов. Последующие вопросы по вакансии по-прежнему отправляют её текст целиком
(≈ 5k токенов, ≈ $0.0005 за вопрос) — это поведение F5, не меняю (вопрос 4).

## Как проверить
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` — зелёные
- [ ] Вакансия с пробелами в must-have → отчёт: шапка, уточнения (≤ 5, сначала missing),
      категории, сильные стороны / риски, свёрнутый полный список, CTA
- [ ] «Не важно» / «Желательно» → процент, уровень, категории и риски меняются сразу, в Network
      нет запроса к `/api/chat`; «Сбросить» возвращает исходный процент
- [ ] Перезагрузка — отчёт с уточнениями на месте; вопрос «а без Go он подходит?» — модель
      учитывает уточнения и не называет процент
- [ ] Вакансия без пробелов в must → блока уточнений нет; всё `unknown` → «недостаточно данных»
- [ ] Заявка из отчёта: Telegram-сообщение со сводкой и уточнениями (с моком / при наличии
      токена), процент пересчитан сервером; после отправки — «Отправлено» и после перезагрузки;
      заявка из `BriefCard` работает как раньше
- [ ] Мобильная ширина (375 px), тёмная тема, переключатель с клавиатуры
- [ ] Тесты: правило выбора уточнений (порядок, лимит 5, только must); пересчёт с `none` / `nice`
      (через `computeMatchScore`); сильные стороны / риски; схема `data-priorities` и строка для
      модели; guard; `leadRequestSchema` (оба варианта, лимит размера); `formatLead` для отчёта
      (экранирование, пересчёт на сервере); UI `MatchReport` (рендер, клик пересчитывает,
      сброс, состояния pending / error / null, «Отправлено»)

## Открытые вопросы
1. **Уточнения локально в отчёте вместо tools `askRequirementPriority` + `showMatchReport`** —
   ок? Предлагаю так (см. «Ключевые решения»): $0, мгновенно, ответ можно менять. Альтернатива —
   как в плане, через модель: ≈ +$0.003 и +5–10 с на вакансию и правка выбора сценария при
   автопродолжении. Если ок — обновлю таблицу tools в ARCHITECTURE §2 и §3.4.
   - **Ответ:** да, уточнения локально в отчёте.
2. **Кого уточнять** — только `must` со статусом `missing` и `partial`, до 5? Предлагаю так.
   `unknown` не спрашиваем (в процент не входит), он в рисках как «уточнить на собеседовании»;
   `nice` не спрашиваем (вес и так малый).
   - **Ответ:** принято предложение.
3. **Полный список требований** свёрнут по умолчанию? Предлагаю свернуть: шапка, уточнения,
   категории и риски уже отвечают на вопрос «подходит ли», а список из 15–25 пунктов делает
   отчёт длинным в чате.
   - **Ответ:** принято предложение.
4. **Повторная отправка вакансии в последующих вопросах** (~5k токенов на вопрос) — оставить, как
   в F5? Предлагаю оставить: вопросы вроде «почему React частично?» нуждаются в тексте вакансии,
   а цена ≈ $0.0005 за вопрос. Альтернатива — после анализа отправлять только анализ, без текста.
   - **Ответ:** принято предложение.
5. **Лимит заявок общий** для брифа и отчёта (1 в сутки на IP)? Предлагаю общий: это один и тот
   же человек и один канал.
   - **Ответ:** принято предложение.

## Дополнение (после реализации)
- **`data-priorities` лежит в конце сообщения анализа**, а не сразу после `tool-analyzeVacancy`:
  AI SDK превращает data-часть в сообщении ассистента в его текст, и посередине она оказалась бы
  между вызовом tool и его результатом.
- **Ответы применяются только к требованиям из правила уточнений** — и в отчёте, и на сервере при
  расчёте заявки. Подделанное «Vue → не важно» в теле `/api/lead` не меняет процент.
- **Пока сообщение стримится, переключатели неактивны**: правка во время стрима перезаписалась бы.
- **Доступность переключателя**: `toggle-group` из reka-ui — группа кнопок с `aria-pressed`,
  подписью «Важность: Go» и навигацией стрелками, а не `radiogroup`. Выбранный вариант выделен
  цветом `primary` (стандартный `bg-muted` в тёмной теме почти не виден).
- `lead.description` в i18n стал объектом `{ brief, report }`; заметка о `data-lead` для модели —
  без «from the brief card».
- Логика отчёта (правило уточнений, пересчёт, сильные стороны / риски, строка для модели) —
  чистые функции в `shared/match/report.ts`, общие для клиента, `/api/chat` и `/api/lead`.
- **Не проверено вживую:** отправка заявки в Telegram (нет токена бота — покрыто тестами с моком
  `fetch`) и ответ реальной модели на вопрос после уточнений (запросы к LLM не тратил — строку
  для модели проверяет тест `/api/chat`). Отчёт, пересчёт, сброс, сохранение после перезагрузки,
  отсутствие запросов к `/api/chat`, ширина 375 px и обе темы проверены в браузере на
  production-сборке с подложенной историей.
